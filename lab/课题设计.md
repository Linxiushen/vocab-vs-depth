# 课题：固定参数预算下，中文小模型的词表与深度取舍

2026-09-14 修订。当前进度和本轮实测数值见项目根目录 README 与
`lab/results/`。9 月 10 日的原稿保存在同目录历史稿，里面的估算和结论
不能直接作为实验结果引用。

## 学习目标

完整经历一次语言模型预训练：准备语料、训练 tokenizer、随机初始化 Transformer、
反向传播、保存与加载 checkpoint、独立验证和文本续写。先前完成的 30M 冒烟运行
已经覆盖模型训练与权重保存；64M 对照实验和 SFT 是后续阶段。

研究问题是：在约 64M 参数下，用更大词表节省文本 token，是否值得减少一层
Transformer？这是本项目的可验证问题，不主张“此前无人研究”。

## 实验配置

| 用途 | tokenizer | vocab | 层数 | hidden | FFN | 参数量 |
|---|---|---:|---:|---:|---:|---:|
| 已完成的冒烟练习 | 官方 MiniMind | 6,400 | 8 | 512 | 1664 | 约 30.03M |
| 正式 A | 本次 BPE 合并序列的 6.4K 前缀 | 6,400 | 8 | 768 | 2432 | 约 63.91M |
| 正式 B | 本次训练的 16K BPE | 16,384 | 7 | 768 | 2432 | 约 64.21M |

A/B 的参数差约 0.46%，是近似匹配，不是完全相同。两者使用相同预分词规则、
特殊 token、训练语料和 BPE 合并序列；A 停在较早的合并位置。
官方 6.4K tokenizer 另作参考，不能把它与 B 的差异全归因于词表大小。

输入 embedding 和输出投影共享权重。实际量化文件大小、解码速度和端侧性能
要等导出后测量，不能由参数数目直接宣布相同。

## 数据与隔离

原始预训练语料共 1,270,238 行，SFT 数据已下载但尚未训练。
新冻结数据位于 `lab/data/v2/`：

- `val.jsonl`：固定并打乱顺序的 1,943 篇文档。
- `tokenizer_train.jsonl`：从全部训练行做 reservoir sampling 的 30 万条样本。
- `manifest.json`：文件 SHA-256、采样 seed、行数和精确重叠审计。

旧模型训练完成后曾重新划分验证集，导致旧全局验证集含 57 篇已训练文本。
新划分按文本内容哈希，把验证文本的所有精确副本从新训练集中排除，同时排除
旧 smoke 训练已经见过的文本。近重复检测尚未进行，不能据此宣称完全无泄漏。

新划分和所有旧文件分开保存，旧 checkpoint 继续配官方 tokenizer。
不能给同一份权重直接换一个新 tokenizer。

## 第一阶段：词表实验

只使用训练集学习 BPE。压缩评测使用完整的固定验证原文，同时报告：

1. 所有文档、含中文文档、不含中文文档各自的字符数、UTF-8 字节数和 token 数。
2. 字符/token、字节/token，以及相对于同来源 6.4K 词表的 token 减少比例。
3. 编码后解码是否逐字一致、特殊 token 的 ID 和保留标志是否一致。
4. 固定序列长度下的 padding 比例和截断文档数。

“含中文”是按 CJK 字符检测分组，不等同于纯中文。
旧的 1.19 字符/token 来自六个人工选的句子，不是全语料统计。
压缩改善不等于 BPB 改善，也不自动等于训练加速；不存在“提升不到 30% 就无胜算”
这样的硬阈值。

## 第二阶段：64M 训练实验

`lab/configs/arms.json` 固定两组模型。
`lab/run_pretrain.py` 复用 MiniMind 原训练器，并隔离每次运行的配置、数据摘要、
日志、权重和 optimizer checkpoint。

- `--profile check`：16 条文档、短序列，只验证加载、梯度更新和保存。
- `--profile full`：冻结训练源文档的一轮预训练，用于探索性复现。
- 两种模式均从随机初始化开始，不加载现成模型权重。
- 现有训练器按文档截断并 padding。full 模式固定原始文档集合，但两种
  tokenizer 在 512-token 截断下实际读到的原文字节可能不同。
  所以这只是“相同文档和 token 窗口”的比较，不得写成“严格相同训练字节”。
- 若要回答严格等原文预算的问题，应先生成两种 tokenizer 都能容纳的共同文本分块，
  或实现完整文档 packing，再记录实际监督 token/字节数量。
- 等计算量实验需独立计时和计算成本统计，不能只比较相同步数。
  `6ND` 是粗略模型，不完整计入注意力和词表投影等差异。
- 先做单 seed 探索，再用多个 seed 检查结论是否稳定。当前没有可报告的 A/B 胜负。

## 第三阶段：模型评测

新 `lab/eval_bpb.py` 协议为 `all_body_tokens_bos_per_chunk_v2`：

- 两个模型评分同一批完整原文；不因 token 截断而比较不同文本。
- 每块加 BOS，最多 510 个正文 token；所有正文 token 恰好计分一次。
- 不计 EOS 的损失，分母使用原始全文 UTF-8 字节数。
- 长文分块重置上下文，所以必须报告窗口与分块协议。
- 原始文本必须编码解码无损，否则直接报错。

```text
BPB = 总正文 NLL(nats) / (ln(2) × 总原文 UTF-8 字节数)
```

同词表可以对照 token loss/PPL；跨词表比较优先用上述同协议 BPB。
BPB 不是衡量任务能力的唯一指标，之后还要观察续写、指令跟随和运行性能。
旧 BPB 数字使用截断协议及不同数据，不能与 v2 直接作升降比较。

## 如何解读训练日志

30M 冒烟使用 40,000 篇文本、batch=8、accumulation=4、seq=512。
日志的 5,000 step 是 micro-batch，共 1,250 次 optimizer update。
20.48M 是包含 padding 的处理位置数。有效监督 token 数见
`lab/results/smoke-audit.json`。

每条日志是单 batch loss。有噪声是正常的，不能从一两个点推断学习率导致加速，
也不能预设“500 步必须到 5.0”或“SFT loss 小于 0.3 必然过拟合”。
应结合固定验证集、学习率、梯度及实际数据预算判断。

`ln(V)` 对应均匀概率预测器，实际随机网络不一定精确达到该值。
训练集经验 unigram 熵不能直接冒充独立验证基线。
一次训练的 loss 低于另一份语料的熵，也不足以严格证明利用了上下文。

历史吞吐测试不是热稳定性验证：单次当前显存读数不是峰值显存；
纯 BF16 权重训练不等于混合精度训练；没有系统 thermal warning 也不能排除降频。
后续正式计时独立运行，并记录实际窗口时间。

## 学习顺序

1. 读 `lab/第一课-一次预训练到底发生了什么.md`，观察 tokenizer、label shift 和更新次数。
2. 看自己模型的文本续写，以及同协议下随机模型与已训练模型的验证差异。
3. 看 6.4K/16K tokenizer 报告，理解词表参数与文本长度的交换。
4. 跑完 64M 对照实验，记录预算和验证结果。
5. 接一轮 SFT，再测试聊天格式；之后才做量化导出和端侧测试。

词表规模本身不能决定中文知识分数，不能断言“64M 必然随机猜题”。
当前工程验证也不代表已获得一个可用的聊天助手。
